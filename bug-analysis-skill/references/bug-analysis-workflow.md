# Bug 分析八步工作流

## 总览

| 步骤 | 名称 | 输出物 |
|------|------|--------|
| ① | 结构化 Bug 输入 | 标准 Bug 描述模板 |
| ② | 提取问题现象 | 现象列表（不猜原因） |
| ③ | 判断影响模块 | 模块/服务清单 |
| ④ | 推荐日志方向 | 关键词 + 日志路径 |
| ⑤ | 推荐 SQL 方向 | 可执行查询语句 |
| ⑥ | 关联历史 Bug | 相似案例 + 曾用根因 |
| ⑦ | 输出回归范围 | 功能/接口/场景列表 |
| ⑧ | 判断风险等级 | P0～P3 + 理由 |

可选第九步：**人工复核**——对 AI 输出逐项打勾，标注「已验证 / 待验证」。

---

## Step 1：校验输入

- 对照 `bug-input-template.md` 检查必填字段
- 缺项时列出待补充问题，**暂停后续步骤**直至关键信息齐备
- 可基于已有信息进行部分分析，但须标注「基于不完整输入，以下结论待验证」

## Step 2：提取问题现象

**规则**：只描述「观察到什么」，不写「因为什么」。

- 仅列出可观测事实，每条以「-」开头
- 禁止出现「可能」「应该是」「大概」
- 若输入含推测性语句，改写为现象或标注「待验证假设」

**示例**

输入：`支付成功，订单未支付`

输出：

```markdown
## 问题现象
- 第三方支付渠道返回支付成功
- 订单表状态字段仍为「未支付」
- 用户端页面展示与后台状态一致（未支付）
- 存在「支付态 vs 订单态」不一致
```

## Step 3：判断影响模块

- 结合 `module-map.md` 按现象关键词匹配关联模块
- 列出所有可能涉及的服务/模块，标注优先级（P0 直接相关 / P1 间接相关）
- 案例「支付成功、订单未更新」应覆盖：支付服务、订单服务、MQ/消息、库存、优惠券、对账/流水

## Step 4：推荐日志方向

输出格式：

```markdown
## 日志排查建议
| 优先级 | 服务/路径 | 关键词 | 关注点 |
|--------|-----------|--------|--------|
| P0 | payment-service | callback, notify | 回调是否收到、签名校验 |
| P0 | order-service | update status | 更新订单是否执行 |
| P1 | mq-consumer | consume, retry | 是否消费失败、重试堆积 |
```

详见 `log-keywords.md`。

## Step 5：推荐 SQL 方向

- 给出**可直接改参数执行**的 SELECT 语句
- 标注「生产库只读、脱敏，执行前需 DBA/研发确认」
- 详见 `sql-snippets.md`

## Step 6：关联历史 Bug

- 按关键词 + 模块 + 日志特征匹配 `history-bugs.md`
- 输出格式：

```markdown
## 历史 Bug 关联
- [高相似] BUG-2024-088：MQ 消费失败导致订单未更新
- [中相似] BUG-2023-041：支付回调重复，幂等未拦住
```

## Step 7：输出回归范围

区分三级：

- **必测（P0 链路）**：直接受影响的核心流程
- **建议测（关联模块）**：间接关联功能
- **抽测（低关联）**：边界场景

支付问题示例：支付下单、支付回调、订单状态查询、库存扣减、优惠券核销/回退、支付流水、退款全链路、对账任务。

## Step 8：判断风险等级

参考 `risk-levels.md`，给出 P0–P3 及 1–2 句理由。

## Step 9：人工复核清单

```markdown
## 人工复核清单
- [ ] 输入信息完整
- [ ] 现象描述无推测性语句
- [ ] 影响模块无遗漏
- [ ] 日志关键词已按优先级排序
- [ ] SQL 可改参数执行
- [ ] 历史 Bug 关联合理
- [ ] 回归范围分三级
- [ ] 风险等级有理由支撑
```
