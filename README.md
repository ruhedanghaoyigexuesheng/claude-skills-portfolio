## 📖 概述

这不是一堆零散的 Prompt 模板，而是一套**体系化、可联动、可积累**的 AI 辅助测试工具集。

每个技能都包含：
- 📋 **固定步骤的标准化工作流** — 不跳步、不猜测、不编造
- 📤 **结构化输出格式** — 可复现、可交接、可评审
- 🛡️ **防幻觉约束规则** — 证据不足时先追问，而非断言根因
- ✅ **人工复核 Checklist** — AI 产出 + 人工把关的协作模式
- 📦 **领域知识资产库** — 历史 Bug、日志规律、SQL 风险模式可持续积累

### 🐛 Bug 分析 `bug-analysis`

> **8 步结构化 Bug 分析，输出可复现的排查报告**

```
校验输入 → 问题现象 → 影响模块 → 日志方向
    → SQL 方向 → 历史 Bug → 回归范围 → 风险等级 → 人工复核
```

| 亮点 | 说明 |
|------|------|
| 📥 **输入不完整先追问** | 对照 `bug-input-template.md`，缺项列出待补充问题 |
| 🔗 **历史 Bug 关联** | 匹配历史 Bug 库，标注相似度，避免重复排查 |
| 🎯 **回归范围三级** | 必测 / 建议测 / 抽测，不写「相关功能」等模糊表述 |
| 🚫 **禁止无据断言** | 无日志/无数据时不允许猜测根因 |

**输出：** 10 章节结构化 Bug 分析报告（输入摘要 → 人工复核清单）

---

### 📝 日志排查 `log-analysis`

> **7 步日志分析，从杂乱日志中收敛异常根因方向**

```
关键词提取 → 异常类型归类 → 调用链还原
    → 模块定位 → 历史模式匹配 → 风险等级 → 缺失信息清单
```

| 亮点 | 说明 |
|------|------|
| 🏷️ **异常类型自动归类** | `exception_type_map.md` 区分 timeout、duplicate key、connection refused 等 |
| 🔗 **服务调用链还原** | 按 traceId 还原分布式调用路径，定位首次异常点 |
| 📊 **历史模式匹配** | `log_pattern_history.md` 积累的常见错误模式快速匹配 |
| ⚠️ **证据不足输清单** | 信号不足时输出「缺失信息清单」，而非硬猜根因 |

**内置：** 7 种仿真日志样例（支付锁超时、重复键、连接拒绝、MQ 消费异常等）

---

### 🗄️ SQL 分析 `sql-analysis`

> **8 步 SQL 性能风险识别，告别「慢就加索引」的粗暴做法**

```
输入校验 → SQL 结构 → 索引使用 → 数据量评估
    → 执行计划 → 风险信号 → 优化建议 → 验证方式
```

| 亮点 | 说明 |
|------|------|
| 📐 **强制输入契约** | 必须提供 DDL + 数据量 + EXPLAIN，缺一则列待补充项 |
| 🚨 **8 种高危信号** | 全表扫描、深分页、隐式转换、函数包裹索引、低基数索引等 |
| 📝 **优化建议带验证** | 每条建议附 `验证方式`，如「加上索引后 EXPLAIN 应显示 Using index」 |
| 📋 **事故模式库** | `sql_incident_patterns.md` 记录历史 SQL 事故，辅助模式匹配 |

**内置：** 5 个练习 SQL + EXPLAIN 结果样例 + 完整/错误报告对照

---

### 🔄 回归测试 `regression-test`

> **7 步精准回归范围分析，回答「这次发布到底要测什么」**

```
解析改动 → 识别上下游影响 → 业务链路补全
    → 关联历史 Bug → 标记风险等级 → 输出清单 → 人工复核
```

| 亮点 | 说明 |
|------|------|
| 🗺️ **模块影响映射** | `module-impact-map.md` 定义模块间上下游依赖关系 |
| 🔗 **业务链路知识** | 内置支付、订单两条完整业务链路（可扩展） |
| 📊 **历史 Bug 驱动** | 自动匹配历史 Bug CSV，推荐高频故障场景回归 |
| 🎨 **P0–P3 风险标记** | 每个回归项标注风险等级 + 触发原因，不是「全测一遍」 |

**输出：** 可执行回归清单（含风险等级、触发原因、历史 Bug 关联、建议优先级）

---

### 🤖 Prompt 测试 `prompt-test`

> **8 步工程化 Prompt 质量验证，5 维度覆盖**

```
明确目标 → 正常样本 → 稳定性×3 → 边界输入
    → 错误输入 → 多轮一致性 → 幻觉风险 → 测试报告
```

| 维度 | 验证什么 | 不合格信号 |
|------|----------|------------|
| 🔁 **稳定性** | 同输入 × 3 次，核心字段不漂移 | 有时有边界值，有时没有 |
| 🔲 **边界输入** | 信息过少/过多时仍清晰 | 需求极短却乱编完整方案 |
| ❌ **错误输入** | 识别矛盾，先质疑再生成 | 顺着错误需求硬写 |
| 🔄 **多轮一致** | 后续轮次遵守前面规则 | 第二轮忘掉输出格式 |
| 🌀 **幻觉风险** | 证据不足时克制下结论 | 日志一行就断定根因 |

| 亮点 | 说明 |
|------|------|
| 🧪 **7 个测试样本** | 从正常到异常的全覆盖测试集（01–07 号） |
| 📊 **稳定性≥3 次** | 必须新开对话独立运行，禁止同轮混跑 |
| 📝 **不通过给 v2** | 不通过时输出修改版 Prompt，不只报告问题 |
| ✅ **通过/不通过结论** | 明确判定标准，不靠感觉评价 |

在 Claude Code 中，将对应目录加载为 Skill：

```
# Bug 分析
@bug-analysis/SKILL.md
订单支付成功但状态显示未支付，请帮我分析。

# 日志排查
@log-analysis/SKILL.md

# SQL 分析
@sql-analysis/SKILL.md

@regression-test/SKILL.md
支付回调模块有更新，请生成回归测试清单。

# Prompt 测试
@prompt-test/SKILL.md
这是我的 Prompt：[Prompt 内容]，请执行完整测试。
```

```
@ai-test-workflow-toolbox/SKILL.md
Bug、日志、SQL 联动分析：[描述你的问题]
```

工具箱会根据问题复杂度，自动路由到联动工作流，按 Bug→日志→SQL→回归的顺序逐步执行。

## ✨ 设计理念

### 🎯 不是 Prompt，而是 Workflow

每个技能不是一个「万能 Prompt」，而是**固定步骤的工作流**（7–8 步）。步骤之间的先后关系经过设计，确保分析不遗漏、不跳步。

### 🛡️ 默认不信任 AI 的结论

内置了大量「防幻觉」约束：

- 缺少输入 → 先追问，不编造
- 证据不足 → 输出「缺失信息清单」
- 每个输出 → 附带「人工复核 Checklist」
- Bug 分析报告不允许出现「可能是」「应该是」

### 📈 可积累的领域知识

`references/` 和 `assets/` 目录下的知识库是**活的**——团队在使用过程中可以不断补充：

- 新的历史 Bug → 加入 `history-bugs.md`
- 新的日志模式 → 加入 `log_pattern_history.md`
- 新的 SQL 事故 → 加入 `sql_incident_patterns.md`
- 新的业务链路 → 加入 `业务链路-*.md`

### 🔗 独立可用，组合更强

5 个专项技能可以各自独立使用，也可以通过 Toolbox 联动。类比 Unix 哲学：每个工具做好一件事，通过管道组合释放更大价值。
